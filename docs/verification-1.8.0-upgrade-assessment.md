# GetMCP 1.8.0 upgrade assessment

Date: 2026-11-01. Status: **reviewed 1.8.0 compatibility and automatic migration implemented; release and real-provider verification remain open**.

The supplied `getmcp-1.8.0.zip` has SHA-256 `6e97570dce54a8cd41d7e349938377dc88ea4a2bb341cdf45fc0be6abf3a9d6e`. The checked-out add-ons were Extensions 1.4.0-beta.1 at `6ea4c96` and Telegram 0.1.1 at `033187c`. This is an assessment of this exact package, not a claim about other 1.8.0 builds.

## Implementation and evidence

The repository now contains the reviewed, hash-pinned 1.8.0 compatibility profile. A synthetic 1.7-to-1.8 HTTP rehearsal using the actual workspace source and runtime automatically converted a standard server, remote connection and project gateway, retained encrypted personal grant bytes, and exercised access, refresh, gateway tools, resources, prompts, read-only denial and revocation. A modified adapter mapping was refused before loading. The fixture bootstrap only supplies synthetic upstream responses and limits migration to its disposable server IDs.

The actual-source rehearsal also passed under WordPress 6.2.2 and PHP 8.2.8, including the project Gateway, original access and refresh grants, an API-key Gateway, remote tools, resources and prompts, and the administrator warnings. A separate rehearsal upgraded core while the add-on was inactive: reactivation preserved the legacy and native grants, flagged the unverifiable built-in Gateway history, and did not invent member access. Rolling core back to 1.7 automatically restored the recorded sign-in types and the original project-Gateway token, refresh grant and API-key Gateway behavior. This used the shared fixture's restored database originally created on WordPress 7.1, plus an explicitly synthetic paid-license double; it is not proof of a clean 6.2 installation or a real license-server response.

Additional synthetic tests on the real loader cover independent migration groups and retries, native branding and PII settings, fixed and header-derived path variables, published Launch Kits, Health and Google personal-provider gateway members, Instagram Page-token gateway execution, legacy and native management tools, and native provider-editor secret preservation. Caller-selected upstream hosts remain deferred under the stricter 1.8 security rule. The Page test preserves the encrypted vault, refuses an altered messaging endpoint and another Page, and sends one synthetic ambiguous write without retry. Core and add-on connection editors coordinate through the core authentication lock; stale add-on saves with a revision return a conflict. Real Google and Meta consent, actual provider acceptance, multisite, and unreviewed settings and gateway dependency shapes are not proven. Unsupported records remain protected and are flagged for administrator review.

A temporary PDO image and disposable PostgreSQL service in the same shared fixture additionally tested reviewed MySQL/MariaDB and PostgreSQL connectors and their dependent gateways. Synthetic rows remained readable through the migrated gateways without granting direct access; the encrypted connector settings stayed byte-identical, read-only mode refused an insert, and explicitly enabled writes succeeded against disposable tables. Malformed read-only values, unreadable secrets and unknown SQL actions deferred conversion.

Disposable FTP, explicit and implicit FTPS, and SFTP services passed migration, delegated access, encrypted credential preservation, read-only refusal and synthetic writes. FTPS tests verified certificate hostnames; SFTP tests covered pinned host identities, password and private-key login, encrypted key passphrases and refusal of a mismatched passphrase. In the supplied native core, reading a short FTP file with the default range produced a partial-transfer error against this fixture; the successful FTP/FTPS reads used an explicit byte bound equal to the file length. The same range behavior exists in the 1.7 code.

A disposable IMAP service and a non-relaying SMTP sink passed password and XOAUTH2 credential migration, delegated access, IMAP and SMTP transport modes, certificate-hostname refusal and invalid-token refusal. Synthetic SMTP failures after receipt were dispatched once. These tests did not contact real mail providers or recipients.

The 1.8-specific add-on screens have also been exercised in a disposable browser fixture for gateway and remote editing, headers, settings, personal connections, provider allowlists and subscriber refusal. Core retains its own native administration bundle. These browser checks did not use live accounts or provider consent.

The reviewed 1.8 adapters retain personal provider grant selection, user-specific caching, safe write retries, and provider protocol envelopes while preserving native delegated-auth checks. The native server editor adapter also keeps reviewed Google Health OAuth options under the core authentication lock, and health execution and logging adapters retain the add-on's privacy behavior. The isolated synthetic Google Health suite passed 94 checks, including grant refresh, access refusals, gateway routing, logging, editor conflict handling and invalid endpoint refusal; actual Google application consent and live provider behavior were not exercised. The adapters are hash-checked when the 1.8 profile loads; the synthetic results do not establish compatibility with every provider or configuration.


Automatic preparation separates old encrypted upstream-grant rows from the incompatible native table without decrypting them; mixed stores, interrupted moves, conflicting copies and rollback are covered by synthetic database rehearsals. A conflicting destination defers the core schema update and is left untouched. For the reviewed already-upgraded layout, the add-on now repairs the native table's missing `id` primary key after grant separation. It retains the `(server_id,user_id)` uniqueness boundary and refuses unknown columns, remaining legacy rows, and foreign-key references. A local 1.7-to-1.8 rehearsal with the add-on inactive during the core upgrade verified automatic separation and repair on reactivation, preserved both an original personal grant and a native grant created in the interim, and passed 18 HTTP Gateway and grant checks. These tests do not cover every supported database engine or crash point.

Pending legacy authorization codes retain their original 1.7 redirect binding when that exact value is still available in the original transient. Missing, expired, unrelated or already-bound records are left alone. A local HTTP rehearsal issued access, refresh and pending-code grants on 1.7, then manually changed a synthetic standalone server to the 1.8 sign-in type: access, refresh and code exchange succeeded, and removing the allowed user denied both access and refresh. This is not evidence that arbitrary server settings, clients, scopes or grants can automatically migrate.

The current user explicitly prioritizes Extensions and excludes Telegram from this implementation. The 1.8 compatibility profile automatically converts reviewed standard, remote and project-gateway servers. It preserves the original server fields and encrypted personal grant, records the converted IDs for a 1.7 rollback, refuses unsupported or ambiguous records, and keeps unconverted endpoints guarded. Administrators see a warning when a server is deferred or historic built-in Gateway delegation cannot be verified. For missing Gateway history, current access rules are retained rather than inventing a grant, as requested by the user.

In local synthetic tests, the bridged gateway lists and calls remote tools, reads resources, gets prompts, uses and refreshes the correct user's original per-user upstream OAuth grant, refuses a removed member and does not forward the downstream bearer. A native-member rehearsal exercises tools, resources and prompts with core 1.8 availability filters and delegated-auth safeguards. For the built-in Gateway, a pre-upgrade signed snapshot records eligible legacy members under unchanged Gateway settings. OAuth selected and all-server modes passed 1.7-to-1.8 HTTP tests with the original token and refresh grant; selected API-key and public Gateways also passed with the original key or public access. Those tests included legacy remote servers with no upstream authentication and shared encrypted credentials, tools, resources and prompts, and refused changed credentials or removed members. A later-created Gateway key cannot inherit the prior delegation. New native members retain the 1.8 per-member check, and changed gateway settings invalidate the exception. Sites upgraded before a snapshot exists cannot safely reconstruct historical Gateway delegation from current settings alone and receive an administrator warning. Creation, editing, secret-free management responses, custom-header preservation, scoped deletion, client metadata coexistence and subscriber access refusals have focused local checks. The end-to-end HTTP rehearsal uses an explicitly test-only bootstrap for synthetic fixtures; it does not prove real-provider acceptance.

The old built-in Gateway inspected at most 500 active servers ordered by name. A synthetic 501-server test confirms the snapshot keeps members provably inside that limit and excludes the rest. If equal names straddle the 500-server boundary, the tied members cannot be reconstructed reliably and are deferred; they are not evidence of a seamless transition for those installations.

The separate manual review action accepts **empty standard servers only**: no tools, resources, prompts, custom settings, upstream grants, OAuth clients or OAuth grants; no legacy or native project gateways and no enabled original gateway. It checks the administrator capability and review fingerprint, uses a serializable transaction on InnoDB tables, and preserves every server field except `auth_type`. The automatic bridge described above handles additional reviewed cases. Neither path alone establishes compatibility with every possible 1.8.0 configuration.

Local verification of this limited path: 33 isolated planner assertions; a 1.7.0-to-1.8.0 WordPress/MariaDB fixture rehearsal with 39 assertions, including real local OAuth client registration, code exchange, authenticated MCP `tools/list`, anonymous refusal and immediate denial after allowlist removal; and eight REST/admin-rendering assertions. The authorization code was seeded for HTTP testing; actual browser consent and real provider acceptance were not tested. The fixture's database and original 1.7.0 source mount were restored afterward. The CLI tests use synthetic records and are not a production migration.

## Results

An initial upgrade rehearsal used the shared `getmcp-telegram-qa` fixture, WordPress 7.1.3, PHP 8.3.28, MariaDB 11.4 and synthetic remote-server, gateway and OAuth-grant records. The 1.7.0 database was backed up before the rehearsal. GetMCP's database version advanced from 1.26 to 1.35. The two synthetic records retained their old `server_kind` values (`remote-mcp`, `gateway`), but both received the new native `kind=standard`. Before the 1.8 profile was implemented, Extensions correctly refused the unreviewed core and its persistent guard classified the synthetic remote endpoint as blocked. The later reviewed-profile results are described above.

The 1.8.0 native grant lookup was exercised with a deliberately nonmatching hash against the synthetic legacy grant. The row was present before lookup and deleted after it. This proves the mismatch deletion behavior; it does not mean that an ordinary upgrade necessarily invokes this lookup for an unmigrated record. The core schema migration added `config_hash` and `created_at` to the legacy table, but did not add the native schema's `id` column or replace the composite primary key in this fixture. The old row remained until the explicit test lookup.

Before Telegram was excluded from the task, an initial signature contract passed for its 44 catalog tools; the then-unreviewed 1.8 integration did not complete. No Telegram implementation changes were made as part of the current work, and no present compatibility claim is made for it.

Afterward, the fixture's database and normal 1.7.0 source mount were restored. The database version returned to 1.26, Extensions reported its reviewed 1.7.0 profile ready, Telegram diagnostics returned ready, and the synthetic records were absent. Dumped `getmcp_servers` and `getmcp_telegram` rows matched the pre-test snapshot. The private backup is outside the repositories and must be treated as sensitive.

## Mapping and blockers

| Area | Extensions | GetMCP 1.8.0 | Required transition |
| --- | --- | --- | --- |
| WordPress sign-in | `auth_type=oauth`, `auth_config.provider=getmcp`, `allowed_user_ids` | `auth_type=wordpress`, same allowlist key | Preserve the exact IDs, server identity, credentials and existing grant semantics. Check existing issued OAuth grants and revocation behavior; do not assume the type change alone preserves sessions. |
| Remote MCP | `server_kind=remote-mcp`, `settings.remote_mcp` | `kind=remote`, `settings.remote` | The reviewed bridge retains legacy identity, settings, encrypted credentials and publication behavior; native connections remain separate. Unknown shapes are deferred. |
| Personal upstream grants | Encrypted rows in `getmcp_upstream_connections`, with the old configuration hash inside the encrypted payload | Same table name, new `config_hash` column and a different hash algorithm; native credential representation retains only selected token fields | Preserve and validate legacy ciphertext before any native lookup, account for per-user client registrations and refresh metadata, and establish safe rollback or explicit reconnection. Never set a new hash without proving the grant belongs to the unchanged upstream configuration. |
| Project gateways | `server_kind=gateway`, member IDs in `settings.gateway.server_ids`; membership delegates access independently of a member's direct allowlist | `kind=bundle`, members in `getmcp_bundle_members`; native policy checks member access and refuses remote members | The add-on bridge preserves reviewed legacy membership and delegation without widening direct access. Native bundles do not provide an equivalent for every legacy gateway, and unreviewed shapes remain guarded. |
| Telegram | Requires reviewed Extensions OAuth and explicitly permits only core 1.7.0 in diagnostics | Native WordPress sign-in and changed gateway APIs | Adapt and test publication, account-owner restrictions, direct access and gateway behavior without weakening the existing private-account boundary. |

Existing feature switches and the persistent endpoint guard are part of the transition. The add-on also owns marketing, Google Health, catalogue, custom headers and other functions that are not retired just because core now includes OAuth and remote servers. A native gateway can reject remote members and different access policies can suppress members; preserving IDs alone is not behavior parity.

## Migration design and acceptance gates

1. Build a read-only, secret-redacting inventory and per-server plan against both schema versions. Detect unsupported memberships, conflicting native edits, disabled modules, existing native records and unrepresentable remote configurations. Do not alter live state during preview.
2. Keep protected endpoints fail-closed during upgrade and partial failure. Provide a reviewed compatibility path for still-needed add-on features and a recovery path before replacing the guard. Preserve the original database and WordPress encryption salts.
3. For eligible individual servers only, validate and convert configuration using the native APIs, preserve IDs/slugs and compare allowlists. Preserve or explicitly reconcile existing credentials and grants, use conflict detection and idempotent checkpoints, and reject incomplete conversions without deleting the source. Restart in-progress OAuth exchanges where necessary.
4. Handle incompatible gateway members explicitly. Preserve the existing delegation through a tested compatibility path, or present a precise per-gateway review of changed behavior. Do not silently broaden direct access or remove members.
5. Exercise successful, empty-list, denied-user, concurrent-change, corrupt-secret, rollback and retry cases on a snapshot of the shared fixture. Verify native and add-on endpoint behavior, actual stored state, per-user refresh, gateway tools, Telegram publishing and disabled modules. Run both supported old-core and 1.8.0 tests sequentially; include real-provider and browser acceptance as separate gates.

No release, customer-site upgrade, production change, hosted CI run, or migration of actual accounts was performed. Preserve the persistent guard and complete release, environment and real-provider verification before making broad compatibility claims.
